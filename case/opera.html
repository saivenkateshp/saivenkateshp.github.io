🎼 Search Engine for Opera Music

A vertical search engine built end to end, comparing link-analysis ranking, clustering and query expansion side by side with Google and Bing.

01Problem

General search engines are tuned for everyone. The project asked how far a domain-specific engine for opera music could get by crawling its own corpus and trying different ways to rank and expand results, and how those results compare with Google and Bing for the same query.

02Architecture

  • Crawl: Nutch injects seed URLs, then generates, fetches, parses and updates its crawl DB, and dumps the link DB.
  • Index: pages are indexed into the Solr core nutch for full-text retrieval.
  • Link analysis (offline): webgraph.py builds the link graph with NetworkX and writes PageRank (α = 0.85) and hub/authority scores.
  • Query time: the Flask endpoint takes query and type: page_rank, hits, three clustering modes, or association / metric / scalar query expansion.
  • UI: radio buttons pick the mode; results render next to live Google and Bing frames for comparison.

03Key decisions & trade-offs

Nutch + Solr instead of a hand-written crawler

Why: Politeness, URL normalization, deduplication and a link database come built in, and Solr gives solid full-text relevance out of the box.

Trade-off: A heavy Java toolchain to set up and tune for a student-scale project.

Retrieve, then re-rank

Why: Solr returns the top 50 text matches, and the top 20 are re-ordered by link-analysis scores. Text relevance decides what's eligible; authority decides the order. It's the same two-stage pattern modern RAG systems use with rerankers.

Trade-off: Re-ranking only within Solr's candidates means a highly authoritative page with weak text match is never surfaced.

Link scores computed offline

Why: PageRank and HITS run once over the whole graph and are looked up at query time, so query latency stays low.

Trade-off: Scores go stale until the batch job runs again after a new crawl.

Pseudo-relevance-feedback query expansion

Why: Association, metric and scalar clusters built from the top results add related terms, which helps short queries such as a single composer's name.

Trade-off: Expansion can drift away from what the user meant, which is why it's an explicit mode rather than the default.

04Results

The engine indexed 120,000+ pages and served eight ranking and expansion modes through one API. The side-by-side UI made it easy to see where link analysis helped (authoritative reference pages rising for broad queries) and where expansion helped (short queries gaining relevant results).

05What I'd do differently

  • Evaluate with a labeled query set and standard metrics (nDCG@10, MRR) instead of comparing visually with Google and Bing.
  • Combine BM25 and link scores in one weighted formula and tune the weight, rather than a pure re-order.
  • Compute and evaluate distinct assignments for each clustering mode.
  • Add dense retrieval (embeddings) for hybrid search, and containerize Nutch + Solr for reproducible setup.
